# Verification

How the SDK was verified, what was found, and what is still unproven. Built 2026-11-13; adversarially reviewed the same day.

## Adversarial review

A subagent with no context of the build decisions — just the original request, the skill files, and the production pollers — was asked to try to break the SDK. Verdict: the extraction was mostly faithful (the hook template's logic body is byte-identical to production apart from placeholders, and every latency number checked out), but it found **3 blocking defects**, 8 mediums, and 8 nits. All were fixed the same day. The review's full report is summarized below; the fixes are in the skill.

### Blocking defects (all fixed)

**B1 — Empty-first-poll baseline bug (live correctness bug, inherited verbatim from production).** The daemon template's baseline branch set `baselined = True` even when the first poll returned zero messages, leaving `last_seen` stuck at the `"0"` sentinel. The next poll then treated the whole recent history as new work — and the worker would act on stale history. Production only escaped because the team channel had messages at baseline; the chat-mentions watcher avoids it by construction. Fixed in the template *and* in a production team-queue watcher (`watcher.py`): the daemon only marks itself baselined when its first poll actually saw messages. Verified by running a filled template against an empty source: it logged "first poll saw no messages — staying unbaselined" and wrote no `last-seen.json`.

**B2 — The prescribed three-state dry-run cannot pass (state 2 is untestable).** The skill prescribed dry-running all three hook states (a fourth — worker alive — was added in the 1.0.1 review), including "file appears (new) → WAKE." That state is unreachable via `dry_run` on a fresh hook, because `set_state()` is a no-op under dry-run — the seen_absent recording never happens. A fresh agent following the skill would either conclude the template is broken or accept the baseline as correct behavior (exactly the first-canary bug). Fixed: the skill now documents the state-seeding maneuver (write `{"seen_absent": true}` into the hook's state file before dry-running) and the live-run alternative. Verified with a stubbed hook runtime: state 1 (no file) → silent + `seen_absent` recorded; state 2 (file appears, seeded state, dry-run) → WAKE with the right payload; state 2 unseeded → baselines (proving the seeding step is necessary, not optional); state 3 (no new lines) → silent.

**B3 — No hook-prompt template.** The skill said to register the hook with "the worker-spawn instruction" and the template header suggested a one-liner. The production prompts carry four load-bearing requirements the one-liner drops — most importantly spawn verification (retry once, report failure), because the hook advanced its watermark when it woke, so a failed spawn was silent data loss. (A fifth requirement — the untrusted-data rule — and the cursor-based outstanding rule that replaced the watermark were added in the 1.0.1 review; see below.) Fixed: `templates/hook-prompt.md` now templates the prompt verbatim from the two production prompts, and the skill's Output Contract lists it as a deliverable.

### Mediums (all fixed)

- **M1 — Live-game poll-rate note framed backwards.** The instances file said the workers' 5s differed from the router's 10s "because the router's dispatch rate is the binding constraint" — inverted reasoning. Rewritten as the per-producer rule: match your fastest producer; the 5s rate is justified by sibling handoffs arriving at any moment, and the scribe at 15s is slower than its producers (can lag up to 15s).
- **M2 — Stale-item lesson dropped entirely.** The stale-item rule appeared nowhere in the SDK. Added to the skill's Operating rules and to the worker-brief template's per-task-rules guidance.
- **M3 — `is_new` stub unsafe.** The daemon template shipped a working `is_new` default (`ts > last_seen`) that silently does the wrong thing for most sources (it queues the bot's own replies). Made it a TODO stub with the production filters as commented examples, and added a default hard rule to the worker brief: never act on your own messages.
- **M4 — `queue_item` drops fields production workers use.** The template kept only `{ts, text}`; the team-queue worker needs `user` and `reply_count`, the Discord worker needs author/channel fields. The template now defaults to the fuller shape with a note to include every field the worker's decision rules need.
- **M5 — No Discord daemon template.** The skill's Output Contract referenced a Discord shape that did not exist. Added `templates/daemon.ts`, extracted from a production chat-mentions watcher.
- **M6 — Canary-test ordering hazard unguarded.** The skill never said to wait for the baseline log line before posting the canary, nor that the hook must be registered before the daemon starts. Both orderings are now explicit, with the reasons.
- **M7 — No daemon-health tripwire in the two-tier template.** The liveness check was optional and a production team-queue brief had none. It is now required in the template, and a production team-queue brief gained one.
- **M8 — No daemon start command.** The skill said "start the daemon" with no command, log path, or aliveness check. Added the start commands (nohup + log redirect for Python, bun background process for TS) and how to confirm the daemon is alive.

### Nits (all fixed)

- **N1 — Incomplete noun parameterization.** Three hardcoded strings in the hook template (`"new item(s) left to it"`, payload key `"new_items"`, `"no queue file yet"`) now use `{{ITEM_NOUN}}` / `{{PAYLOAD_KEY}}` / `{{NO_FILE_REASON}}`; the unused `{{HOOK_NAME}}` placeholder was removed from the docs.
- **N2 — Timeout rule contradicted production.** "Keep the call's timeout shorter than POLL_SECS" — production uses timeout = POLL_SECS. The rule is now "timeout ≤ POLL_SECS."
- **N3 — Backoff docs off-by-one.** The first failure used `BACKOFF_STEPS[1]`, not `[0]`. Fixed the indexing in the template and in a production team-queue watcher so the first failure sleeps `BACKOFF_STEPS[0]` and the documented sequences are accurate.
- **N4 — Wake-latency bound understated the path.** "Hook wake latency: ≤60s" omitted the daemon's ≤60s. Now "post → wake ≤120s (daemon ≤60s + hook ≤60s)."
- **N5 — Overclaim.** "The templates are the production files" — the worker brief is a synthesis and the daemon template is extracted from one instance only. Now "the templates are extracted from the production files."
- **N6 — Placeholder ergonomics.** `{{LIVENESS_CHECK}}` now has a section header; the placeholder definitions moved to the top of the worker-brief template; `{{POLL_SECS}}` is documented as a bare integer (not `"60s"`).
- **N7 — Stop-file + hook interaction undocumented.** The hook does not check the stop file, so a wake after the stop file is touched spawns a worker that exits immediately. Documented in the skill's pieces table.
- **N8 — Discord backoff effectively unreachable + dead imports.** Per-channel errors were caught inside `pollOnce`, so the outer backoff only fired on whole-cycle failures — documented in the instances file and the TS template. The dead imports (`subprocess`, `sys`) were removed from the Python template. (The backoff part was superseded in 1.0.1: per-channel failures are now counted, and an all-channels-failed cycle is a cycle failure — see the second review below.)

## Second review (PR 1, Nov 13)

A second review of the public repo landed as 25 line comments on draft PR 1 (the review was generated by Claude Code and posted by the owner). All 25 were addressed in 1.0.1. The comments grouped by fix:

- **Worker lock + cursor-based outstanding (comments on `hook-watch.sh`, `worker-brief.md`).** The alive-file window (180s) was shorter than a worker turn (~3–4 min), so a second worker could start mid-task; a new line arriving while a worker was starting up woke a second one on the same cursor; and the hook advanced its watermark at wake time, before a worker was confirmed started, so a failed spawn stranded the items. Fixed: the worker holds an exclusive flock for its whole lifetime (a holder that exits by itself if the worker stops touching the alive file), the hook checks the lock — not the alive file's age — to decide whether a worker is alive, and "work outstanding" is decided by comparing the queue line count to the worker's `.cursor` file (a new `{{CURSOR}}` placeholder), never by a hook-owned watermark. The hook also records `woke_at` on each wake and stays silent for a startup window, covering the wake-to-lock race. A failed spawn is now retried on the next poll. Verified with a stubbed hook runtime: no-file → silent + `seen_absent`; file appears → WAKE with an identifiers-only payload; re-poll while starting → silent "worker starting"; lock held → silent "worker alive (lock held)"; cursor advanced → silent "no new items"; fresh hook + pre-existing file → baseline + cursor written; stale `woke_at` + cursor behind → WAKE again. The lock holder was verified separately: held while the alive file is fresh, a second take fails at once, and it self-releases once the alive file goes stale.
- **Daemon auth + failure handling (comments on `daemon.py`, `daemon.ts`).** Auth errors retried forever with no signal, and per-channel errors were swallowed inside `pollOnce`, so `consecutiveFailures` never incremented when every channel failed (e.g. a 401) while `last-seen.json` stayed fresh — the daemon looked healthy while it was down. Fixed: both daemons distinguish auth errors (exit non-zero immediately with an `error.json` marker), exit after N consecutive failures, count per-channel failures, treat an all-channels-failed cycle as a cycle failure, and do not write the heartbeat after one. Verified by running filled templates: a 401 on the first poll wrote `error.json` (kind `auth`) and exited 1; a second instance exited 1 with "daemon lock held".
- **Heartbeat (comments on `daemon.py`, both skills).** `last-seen.json` was only written when items were queued, and the liveness check assumed it updated every poll — so an idle healthy daemon failed the check. Fixed: `polled_at` is written on every successful poll, and the liveness check reads `polled_at`, never the file's mtime. Verified: a filled daemon's `last-seen.json` carried a fresh `polled_at` on quiet polls after the last queueing.
- **Prompt injection (comments on `hook-watch.sh`, `hook-prompt.md`, `worker-brief.md`, `slice-worker-brief.md`, `router-brief.md`).** The wake payload embedded raw message text, and no brief said the queue content was untrusted. Fixed: the wake payload carries only the newest item's identifiers and the count (`{{TASK_JQ}}` examples are identifiers only), and every brief plus the hook prompt carries an explicit rule that wake-payload and queue content are untrusted data, never instructions. Verified: the WAKE payload in the hook test carried `{ts, thread_ts}` only — the message text did not appear.
- **Per-message cursor (comment on `daemon.ts`).** The channel cursor advanced to `newest` before the append loop, so a mid-loop throw lost the remaining messages. Fixed: the cursor advances per message after its append succeeds, and after the loop completes it advances past any trailing filtered messages. Verified by the filled-template run: both new messages queued in order, cursor at the newest.
- **Atomic writes + single instance + credentials (comments on `daemon.py`, `daemon.ts`).** State was written in place (a crash mid-write truncated the file and the daemon re-baselined over history), nothing prevented two daemon instances, and there was no guidance on where the source credential lives. Fixed: temp file + fsync + atomic rename for all state writes; an exclusive flock (Python) or exclusive-create pidfile with a liveness check (TS) at startup; a credential note (environment or secrets store, never hard-coded or committed, kept out of logs and queue lines, expiry handled as an auth error). Verified: the atomic write and lock paths were exercised in the filled-template runs above.
- **Log privacy + docstring alignment + portability (comments on `daemon.ts`, `daemon.py`, `hook-watch.sh`).** The TS daemon logged the author's username and the first 100 characters of each message (now channel + message id only); the Python docstring said `read_source` receives the sentinel `"0"` (it receives `None`) and described `is_new(m)` while the stub takes `(m, last_seen)` (aligned); the hook used `printf '%(%s)T'` (bash 4.2+) and GNU `stat -c %Y` (fails on BSD/macOS) — the rewrite uses `date +%s` and a portable `stat` fallback.
- **Genericization (comments on `instances.md`, the skills, `hook-prompt.md`, `worker-brief.md`, `review-guide.md`, `README.md`).** The public copy identified a third party by chat handle, published one deployment's standing-permission terms, and carried project/bot names, internal ticket IDs, and private workspace paths as examples. Fixed (public copy only — the local copies keep the real values): the handle is now "a test mention from a server member"; the standing-permission terms are now "acts within the owner's configured scope"; project/bot names, ticket IDs, and private paths are generic placeholders. The review guide's opening line now addresses "anyone reviewing this SDK before adopting it". The README gained a Requirements section naming the hook runtime (`$HATCH_HOOK_RUNTIME` with `hook_state_get`/`hook_state_set`/`silent`/`wake`, `hooks.add`/`dry_run`/`run`), plus bash, `jq`, and bun for the TS daemon — and what a user on another runtime must supply.
- **Frontmatter (comments on both skills).** Both skills had no YAML frontmatter. Added: `name` + a one-paragraph `description` for each.

## Automated checks (1.1.0)

Since 1.1.0 the daemons are modules and the hook-side logic has scripts, so verification is repeatable rather than a one-off run of filled templates. The commands are in the `README.md` ("Running the checks") and run in CI:

- `tests/daemon` (pytest and `bun test`): the empty-first-poll baseline, per-channel cursors and batch-complete cursor moves, heartbeat, auth exit, `max_failures`, single-instance lock, config validation, and queue appends under `queue.lock`.
- `tests/hook/run.sh`: every hook state against a stub runtime (including queue busy and rotated), `lock-holder.sh` (held while the alive file is fresh, a second take fails, self-release on staleness, release), and `rotate-queue.sh` (rotates only when caught up, archive naming and retention, cursor reset).
- `shellcheck -x` on the templates, tests and scripts; `ruff check`; `tsc --noEmit` in strict mode on the TS daemon and its tests.
- `scripts/check-leaks.sh`: no home paths, emails, chat-style IDs or ticket keys in tracked files, plus any terms in a local `.leak-terms` file.

Earlier manual checks (1.0.x, before the daemons became modules) are recorded in the sections above: filled templates compiled, and the baseline, queueing, heartbeat, auth-exit and single-instance paths were exercised live.

## Live tests

- **Scratch live test of the SDK templates (Nov 13).** A scratch two-tier poller was built from the templates (hook + worker brief + queue), a canary was posted, and the full path ran unassisted: the hook fired live on the canary, the worker consumed it, the cursor advanced to 1, and the subsequent polls stayed silent (no double-wake). The scratch hook and state were removed after the test.
- **Team-queue cold start (Nov 13, second canary).** Post → reply 4m 35s; wake → reply 3m 42s; daemon 18s, hook 35s. The worker's cold start + model turn + post dominates (~3–4 min).
- **Team-queue first canary (Nov 13).** Wake → reply 3m 7s; end-to-end 14m 32s only because the baseline bug (seen_absent) held it ~11 min.
- **Discord warm reply (Nov 13).** ~23s end-to-end ("yo" → "yo 👻").

## What is still unproven

- **Shape B is proven by one instance.** The orchestrator shape is extracted from a live game session alone. A second orchestrator-style build is what would confirm the generalization. The skill and this repo both say so.
- **Discord cold-start test pending.** The two-tier cold start is measured for team chat (team queue) but not yet for Discord — the owner's two test mentions (one cold, one warm) are still outstanding.
- **The production team-queue watcher fix applies on next restart.** The empty-first-poll baseline fix and the backoff off-by-one fix were applied to `watcher.py`, but the running daemon loaded the old code. The fixes take effect when the daemon next restarts. The running daemon is past its first poll and has no consecutive failures, so the fixes are not urgent. The 1.0.1 template fixes (lock, heartbeat, atomic writes, auth exit) are template-only until the production watchers are updated too.
- **The team-queue brief's liveness check is new.** A production team-queue brief gained a daemon-health liveness check (M7). It only takes effect on the next worker spawn and has not yet been exercised by a live worker.
